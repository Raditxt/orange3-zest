# Extra Trees is the easiest to verify from Orange

Of the five candidates, only **A (Extra Trees, Geurts 2006)** has a reference implementation directly in Orange 3.40's bundled Python, namely `sklearn.ensemble.ExtraTreesClassifier`. This class cites the Geurts paper and follows its randomization mechanism, but **its score function differs**. sklearn uses Gini/entropy, while the paper uses the normalized information gain 2·I/(H_s+H_c). **E (multi-label tree)** has a partial equivalent with no extra installation: `DecisionTreeClassifier` with a multi-output y and `criterion="entropy"` is equivalent to ML-C4.5 entropy *as a node impurity*, but the algorithm as a whole is not ML-C4.5. **D (C4.5)** is not in sklearn, which uses CART. Its faithful references are Weka J48 or Quinlan's R8 C code, and both need Java or C outside Orange. **C (UDT, Tsang et al.)** has no Python implementation, but its paper is the easiest to replicate numerically: UCI datasets, a detailed uncertainty protocol, reported accuracies, and Java code that was once released. **B (extenics-based Extension Decision Tree)** has no code, no public dataset, and no accuracy numbers, so it cannot be verified against a reference. The marker **[unverified]** flags findings that have not been checked against a primary source or that still come from a model's summary of a PDF.

Reference versions: Orange 3.40.0 requires `scikit-learn>=1.5.1` ([requirements-core.txt @3.40.0](https://github.com/biolab/orange3/blob/3.40.0/requirements-core.txt)). Source code was checked at the sklearn 1.5.2 tag. The exact sklearn version in the Orange 3.40.0 Windows installer is **[unverified]**. Check with `import sklearn; print(sklearn.__version__)` in the Python Script widget.

## A. Extra Trees: reference available, score function differs

| Aspect | Finding |
|---|---|
| Reference paper | Geurts, Ernst, Wehenkel, "Extremely randomized trees", *Machine Learning* 63(1):3–42, 2006 ([dblp](https://dblp.dagstuhl.de/rec/journals/ml/GeurtsEW06.html)) |
| Callable from Orange 3.40's Python? | **Yes, with no extra installation.** `sklearn.ensemble.ExtraTreesClassifier` and `sklearn.tree.ExtraTreeClassifier` exist in 1.5 and cite Geurts 2006 ([sklearn 1.5](https://scikit-learn.org/1.5/modules/generated/sklearn.ensemble.ExtraTreesClassifier.html)) |
| In Orange itself | There is no Extra Trees learner/widget in 3.40.0. The `RandomForestLearner` pattern (`__wraps__ = RandomForestClassifier`) can be copied with little code ([random_forest.py](https://github.com/biolab/orange3/blob/3.40.0/Orange/classification/random_forest.py)) |
| Same as the paper | For each candidate feature, one threshold is drawn uniformly in the node's [min, max] ([_splitter.pyx 1.5.2](https://github.com/scikit-learn/scikit-learn/blob/1.5.2/sklearn/tree/_splitter.pyx)). No bootstrap (`bootstrap=False`). K=sqrt(n) and n_min=2 for classification. M=100 ([Geurts 2006](https://www.personal.soton.ac.uk/cz1y20/Reading_Group/mlts-2024s/week10/Extremely_randomized_trees.pdf)) |
| Different | (1) **Split score:** sklearn uses gini/entropy/log_loss, the paper uses 2·I/(H_s+H_c). Dividing by H_s can change the order of split candidates. (2) Rounding of K: sklearn uses floor, the paper says "rounded" **[unverified]**. (3) Constant features are handled slightly differently. (4) The paper's random subset split for nominal attributes is not available, so Orange encodes them. (5) NaN is not supported by the `random` splitter in 1.5.2 ([_classes.py](https://github.com/scikit-learn/scikit-learn/blob/1.5.2/sklearn/tree/_classes.py)), so imputation is needed. The paper also drops datasets with missing values |
| Datasets & numbers | 12 classification datasets (mostly UCI: Vehicle, Vowel, Segment, Spambase, Satellite, Pendigits, Letter, Isolet, plus the Waveform/Two-Norm/Ring-Norm generators) with fixed LS/TS sizes. Splits repeated 10 times (50 times for small datasets) ([Geurts 2006](https://www.personal.soton.ac.uk/cz1y20/Reading_Group/mlts-2024s/week10/Extremely_randomized_trees.pdf)). Example ETd errors: Waveform 16.61%, Letter 3.80%, Isolet 7.61% **[unverified; from a PDF summary]** |
| Replicable? | **Yes, statistically** (within ±1 SD). Not to the decimal, because the seeds are not published. Dig44 may not be public |
| sklearn vs paper equivalence | **"Close when configured", not identical.** Exact equivalence needs a custom criterion (Cython) or a Python reimplementation of the paper's score |

## B. Extension Decision Tree: nothing to match against

| Aspect | Finding |
|---|---|
| Reference paper | Extenics theory: Cai Wen, "Extension theory and its application", *Chinese Science Bulletin* 44(17), 1999 ([Springer](https://link.springer.com/content/pdf/10.1007/BF02886090.pdf)). EDT algorithm: Lu & Wang, *JESA* 52(6):559–567, 2019 ([IIETA](https://iieta.org/download/file/fid/23278)). There is also Wang, Xu, Li, ICMSE 2018 ([Atlantis](https://www.atlantis-press.com/article/25895110.pdf)). There is no single canonical paper |
| Algorithm | A matter-element model, a dependent function for classification/discretization, an **ordinary ID3 tree (information gain)**, then an extension transform applied to the trained rules |
| Implementation in Orange 3.40's Python | **None.** sklearn has no equivalent. A possible emulation: discretize with the dependent function K(x), then `DecisionTreeClassifier(criterion="entropy")` or Orange's `TreeLearner`. This is an inference, not a published method |
| Other reference implementations | **None found** (the GitHub search was not exhaustive) |
| Datasets & numbers | Lu & Wang: 200 cases from an internal database, not released, no accuracy metric. ICMSE 2018: a toy example of 10 elderly people, information gain values only. The 2019 GDUT paper in Chinese has not been read **[unverified]** |
| Replicable? | **No.** At most a behavioral check, for example matching gain values on the example table |
| Equivalence | No reference to compare against |

## C. UDT, Tsang et al.: the most replicable paper, code in Java only

| Aspect | Finding |
|---|---|
| Reference paper | Tsang, Kao, Yip, Ho, Lee, "Decision Trees for Uncertain Data", *IEEE TKDE* 23(1), 2011 ([HKU PDF](https://repository.hku.hk/bitstream/10722/152447/1/Content.pdf)). Alternative: DTU, Qin et al., PAKDD 2009 ([Crossref](https://api.crossref.org/works/10.1007%2F978-3-642-01307-2_4)), not yet checked |
| Implementation in Orange 3.40's Python | **None.** sklearn has no equivalent. A `sample_weight` approach that expands each row into s weighted points is only an approximation, not UDT-style split search over pdf intervals (inference) |
| Other reference implementations | Java code (JDK 1.6) from the authors at `cs.hku.hk/~dbgroup/UDT/`. **The URL is not reachable and the license is not stated [unverified]** ([HKU PDF](https://repository.hku.hk/bitstream/10722/152447/1/Content.pdf)). `pyuid3` (Apache-2.0) implements **a different paper**, and its API is not sklearn-compatible ([GitHub](https://github.com/sbobek/pyuid3)) |
| Datasets & protocol | 10 UCI datasets (Iris, Ionosphere, Segment, Vehicle, Satellite, PenDigits, BreastCancer, JapaneseVowel, etc.). Uncertainty is injected as an interval of width w × the attribute range, Gaussian σ = width/4 (uniform also tested), s=100 sample points ([HKU PDF](https://repository.hku.hk/bitstream/10722/152447/1/Content.pdf)) |
| Numbers | AVG vs UDT: JapaneseVowel 81.89% → 87.30%. Iris 94.73% → 96.13% at the best w. Full Tables 2 and 3 not yet extracted **[unverified]** |
| Replicable? | **Yes.** Public data and a detailed protocol, so a NumPy reimplementation can be checked against Table 3 (at least Iris and JapaneseVowel). If the Java code still exists, it can be used as an oracle through a subprocess |
| Equivalence | No sklearn equivalent. Evidence of correctness has to come from the paper's numbers or the authors' Java code |

## D. C4.5: sklearn is not C4.5, J48 becomes the oracle

| Aspect | Finding |
|---|---|
| Reference paper | Quinlan, *C4.5: Programs for Machine Learning*, 1993. Release 8: "Improved Use of Continuous Attributes in C4.5", JAIR 1996 ([arXiv](https://arxiv.org/abs/cs/9603103)) |
| Implementation in Orange 3.40's Python | **None.** The sklearn documentation states that sklearn uses an optimized CART ([sklearn 1.5 §1.10.6](https://scikit-learn.org/1.5/modules/tree.html)). Orange's `TreeLearner` is closer (multiway nominal splits, a missing-value penalty), but uses plain gain without gain ratio and without post-pruning ([tree.py @3.40.0](https://github.com/biolab/orange3/blob/3.40.0/Orange/classification/tree.py)) |
| sklearn vs C4.5 differences | Gini/gain instead of gain ratio. Splits are always binary. No categorical support. `ccp_alpha` instead of pessimistic pruning with CF=0.25 and subtree raising. NaN is sent to one side, not as fractional instances. No MDL correction |
| Other reference implementations | **Weka J48:** "pruned or unpruned C4.5". Defaults CF=0.25, M=2, subtree raising on, MDL correction on. Uses gain ratio and fractional missing values ([J48.java](https://github.com/Waikato/weka-3.8/blob/master/weka/src/main/java/weka/classifiers/trees/J48.java), [C45Split.java](https://github.com/Waikato/weka-3.8/blob/master/weka/src/main/java/weka/classifiers/trees/j48/C45Split.java)). From Python: `python-weka-wrapper3` 0.3.3 (Weka 3.9.7, JPype) ([PyPI](https://pypi.org/project/python-weka-wrapper3/)), **needs a JDK** of the same bitness ([install](https://fracpete.github.io/python-weka-wrapper3/install.html)). **Quinlan's R8 C code** circulates on academic mirrors, license not yet checked. `chefboost` (MIT) is not shown to have C4.5-style pruning or missing-value handling ([GitHub](https://github.com/serengil/chefboost)) |
| Datasets & numbers | The list of datasets and accuracies from Quinlan 1993/1996 **not yet collected**. UCI datasets that exercise missing values (breast-cancer, hepatitis, vote, etc.) **[unverified; general knowledge]** |
| Replicable? | Stronger through **J48 as an oracle on identical splits** (compare tree size and error) than through the old paper's numbers |
| Equivalence | The claim that J48 is built from C4.5 R8 is common, but its primary source has not been collected **[unverified]** |

## E. ML-C4.5: equivalent impurity in sklearn, the algorithm is not

| Aspect | Finding |
|---|---|
| Reference paper | Clare & King, PKDD 2001, LNCS 2168. Multi-label entropy −Σ[p log p + q log q]. Leaves hold a set of labels ([Springer PDF](https://link.springer.com/content/pdf/10.1007/3-540-44794-6_4.pdf)) |
| Implementation in Orange 3.40's Python | **Partial, with no extra installation.** `DecisionTreeClassifier` accepts a 2D y. The `Entropy.node_impurity` code in 1.5.2 gives the mean entropy per output, i.e. the ML-C4.5 entropy divided by the constant L ([_criterion.pyx 1.5.2](https://raw.githubusercontent.com/scikit-learn/scikit-learn/1.5.2/sklearn/tree/_criterion.pyx)). Own test on 300 synthetic datasets: the stump split is the same in **298/300** cases with instance-count weighting, but only **261/300** with Clare & King's "counted twice" weighting. The test was run with sklearn 1.9.1, not 1.5.2, and is unpublished |
| Obstacles in Orange | `TreeLearner` and `SklTreeLearner` do not set `supports_multiclass`, so multi-target data triggers a `TypeError` ([base.py @3.40.0](https://raw.githubusercontent.com/biolab/orange3/3.40.0/Orange/base.py)). The add-on needs its own Learner and probably a dedicated viewer |
| Other reference implementations | **Clare's original C code** (a patch on C4.5 R8), from Aberystwyth, license not stated ([Aberystwyth](https://www.aber.ac.uk/en/cs/research/cb/dss/c45modifications/)). **MEKA** does not list ML-C4.5 ([MEKA](https://waikato.github.io/meka/methods)). **Mulan**: according to Madjarov 2012, ML-C4.5 was run through Mulan, but the Mulan pages do not list it **[unverified]**. **scikit-multilearn** 0.2.0 was last released in 2018 ([PyPI](https://pypi.org/project/scikit-multilearn/)). The **-ng** fork 0.0.8 (2024) only provides problem transformations, not a single multi-label tree ([PyPI](https://pypi.org/project/scikit-multilearn-ng/)). **pyclus** 1.0.2 wraps CLUS PCT, with a sklearn-style API, **needs Java** ([PyPI](https://pypi.org/project/pyclus)). Compatibility of both with sklearn 1.5.x has not been tested |
| Datasets & numbers | Clare & King used their own yeast phenotype data and evaluated rule accuracy (m-estimate, bootstrap), so there is no main benchmark number. **Madjarov et al. 2012** tested ML-C4.5 and PCT on 11 Mulan datasets with fixed splits. Example: Hamming loss on emotions ML-C4.5 0.247, PCT 0.267 **[unverified; from a PDF summary]** ([Madjarov 2012](https://repository.ukim.mk:443/bitstream/20.500.12188/17147/1/PR_2012.pdf), [Mulan datasets](https://mulan.sourceforge.net/datasets-mlc.html)) |
| Replicable? | Yes, against Madjarov on emotions/yeast/scene (numeric features). The match will not be exact with sklearn because pruning and C4.5 details differ. Mulan's yeast ≠ Clare & King's yeast data |
| Equivalence | "Equivalent **as a node impurity**, sklearn is **not** ML-C4.5." Whether ML-C4.5 uses gain or gain ratio, and its leaf labeling rule, are **[unverified]** (check Clare's 2003 thesis) |

## The Python Script widget takes a learner, not a raw sklearn estimator

The Python Script widget provides `in_data`, `in_learner`, `in_classifier`, `in_object` along with the plural forms `in_datas` and so on (all MultiInput), then reads `out_data`, `out_learner`, `out_classifier`, `out_object`. **`out_learner` must be an instance of `Orange.base.Learner`.** If the type is wrong, the widget shows an error and sends None ([owpythonscript.py, master](https://raw.githubusercontent.com/biolab/orange3/master/Orange/widgets/data/owpythonscript.py); [documentation](https://orange3.readthedocs.io/projects/orange-visual-programming/en/latest/widgets/data/pythonscript.html)). So a sklearn estimator has to be wrapped. For A and partial E: a `SklLearner` subclass with `__wraps__` ([base_classification.py @3.40.0](https://raw.githubusercontent.com/biolab/orange3/3.40.0/Orange/classification/base_classification.py)). For custom versions of B, C, and D: a `Learner` subclass with `fit(X, Y, W)` returning a `Model.predict(X)`. The resulting learner can be connected to Test and Score. Three things are **[unverified]**: the widget code that was read comes from master, not the 3.40.0 tag; the re-export path `Orange.classification.SklLearner`; and the pickling risk for classes defined inside the script. For an add-on, put the classes in an importable module. Extra packages (pww3, pyclus, uid3, JPype) are not bundled and must be installed with pip into Orange's Python. Java still has to be installed separately.

## Implications for the choice: ranking by verifiability

| Rank | Candidate | Strongest available evidence | Cost/risk |
|---|---|---|---|
| 1 | **A Extra Trees** | Paper + a reference implementation that cites the paper, inside Orange with no extra installation + public UCI datasets | The score function difference must be documented (or the paper's score implemented). Replication is only statistical |
| 2 | **E ML-C4.5** | Paper + a replicable benchmark (Madjarov/Mulan) + impurity equivalence in sklearn (shown from the code) | The full algorithm does not exist in Python. Needs `supports_multiclass` and a new viewer. A full oracle (original C, Mulan, pyclus) needs C or Java |
| 3 | **D C4.5** | Paper + a strong oracle (J48/R8) | The oracle is only reachable through a JDK + pww3, or C. sklearn and Orange's `TreeLearner` are not C4.5 |
| 4 | **C UDT** | Paper + UCI datasets + a detailed protocol + numbers | No callable implementation. The authors' Java code may no longer be available. Evidence of correctness rests on matching numbers |
| 5 | **B Extension DT** | Application papers only | No code, public data, or numbers, so it does not meet the "paper + reference implementation" standard |

If the criterion is "paper + reference implementation" that can run inside Orange today, **A is the only one that qualifies directly**. Its equivalence claim must be honest: the sklearn configuration is faithful to Geurts' randomization mechanism, but uses a standard impurity criterion. There are two ways forward. First, accept this difference and validate the paper's numbers within ±SD. Second, add a Python version of the 2·I/(H_s+H_c) score and use `ExtraTreesClassifier(criterion="entropy")` as the reference. The second way actually gives the widget a contribution that can be verified against two references at once. E is an attractive second choice if "Extended" is read as an extension to multi-label, but the burden of multi-target integration in Orange is considerable. C is best kept as a follow-up candidate after the availability of the HKU Java code is confirmed. Before quoting numbers in an official document, check them directly in the PDFs: Geurts Table 8, Tsang Table 3, Madjarov Table B1, and Madjarov Section 4.3 (whether ML-C4.5 was really run through Mulan).
